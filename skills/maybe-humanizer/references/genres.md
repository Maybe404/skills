# 体裁与语境

这一份定的是「这段文字属于哪一类、因此哪些规则按什么强度执行」。分诊时先过这里（ALL-PROC-001），体裁定不下来时按 ALL-PROC-003 问一句，不猜。

这里有两张档位表，它们不是同一层，同时命中时各判各的。ALL-G-007 的六个语境档决定按哪一档阈值查，配 ALL-G-008 的三种触发强度；ZH-G-002 的四类中文场景决定输出成什么形态、做不做以语感为目标的第二遍复扫。一段中文文本可以同时落在两张表上，两条都生效；结论方向不一致时按 ALL-PROC-058 的分层处理，两条都在判据层，取更严的一边。

档位只调触发门槛，不调授权。protection.md 里的规则和 ALL-PROC-010 的四组检查在任何档位、任何场景下都不取强度，也不得整组跳过。

## 一 适用与不适用

### ALL-G-001 适用与不适用

**判据。** 适用的是两件事：把已有的中文或英文文字改得不像 AI 写的；只审不改地指出问题。两者都包括段落、文章和长文的结构重写。不适用的有五类：翻译、从零写作、只查错别字、繁体中文、未经授权替真人更换声口。判断方法是看请求落在哪一类，不看文本本身有多像 AI。

**通过条件。** 替真人更换声口在拿到授权之后可以做，按 ALL-PROC-006 的两个授权方向确认。繁体中文划在外面的理由是本次合并的上游没有一个覆盖繁体的用词习惯，声称适用会误导；用户自带繁体词表时按 ALL-PROC-025 用他的表覆盖。

**已知会漏掉什么。** 混合请求判不了：一次同时要求翻译加润色时本条给不出结论，按 ALL-PROC-003 问一句再定。虚构文本的处置不在本条，见 ALL-G-003。

- 正例：一份中文产品分析要求「润色成中文母语表达」，属于改写已有文本，本 skill 的模式表全套生效。
- 反例：把「帮我写一篇关于这个产品的分析」按本 skill 处理，直接产出一篇新稿。违反点：这是从零写作，不在适用范围内，产出的每一句都没有原文可核。

### ALL-G-003 虚构与创意写作不适用

**判据。** 文本是不是虚构。是虚构的，本 skill 的模式表整体不适用：那里的判别信号是叙事结构（未解决的支线、人物选择的模糊性、非线性结构），不是用词和标点。处置顺序固定：先说明模式表不适用，再问用户要不要继续。

**通过条件。** 用户确认要继续时，这个请求已经是创作写作，落回 ALL-G-001 的不适用范围。ALL-G-005 主张虚构文本只豁免「不得编造细节」一条、其余模式表照常跑，与本条冲突，取本条：只豁免一条不够，模式表在虚构文本上给不出有效判定。

**已知会漏掉什么。** 半虚构的东西判不出来：回忆录、案例故事、广告里的场景演绎，它们同时带虚构手法和事实主张，本条不给归属。判定依据是体裁，不是语气，所以一篇写得很有画面感的技术复盘不因此落进本条。

- 正例：面对一份小说手稿，先说明这套模式表是给说明性文字用的，重复用词和片段句在小说里往往是手法，再问对方要不要继续。
- 反例：用词汇和标点类规则审一篇小说，把叙事上成立的重复用词判成 AI 痕迹。违反点：对虚构文本套用了在这个体裁下无效的判据。

## 二 体裁与场景叠加的限制

### ALL-G-002 体裁叠加的限制

**判据。** 体裁在语体之上叠加限制，四类各有可以对照检查的形态要求。正式文章：不用缩写，论证要有结构。邮件：允许问候和落款，不用 markdown 标记。营销文：段落短，结尾只放一个行动点。技术文：保留代码块，术语精确，给数字不给形容词。

**通过条件。** 体裁不明时按 ALL-PROC-003 先问，不猜。用户没有点名要叠体例层时，普通的去 AI 味请求不受体例层影响，也不给一个体裁套用不是为它写的体例。同一条模式规则在不同体裁下结论会相反，技术文里的术语重复要保留、营销文里的重复要删，这正是本条存在的原因。

**已知会漏掉什么。** 本条给的是形态限制，每一档里该优先盯哪一类风险不在这里，归 ALL-G-007，两条各管一半。四类体裁覆盖不到群聊回复和进度同步，中文侧那两类由 ZH-G-002 承担。

- 正例：同一份稿子按邮件体裁改，输出里没有任何 `**` 记号，开头有称呼、结尾有落款，模式表里管加粗的那几条在这里不产生动作。
- 反例：一篇正式文章的改写稿里通篇用 don't、it's 这类缩写，论证也没有分层。违反点：正式文章这一档的两条形态限制都没有生效。

### ZH-G-002 四类场景叠加的限制

**判据。** 先判主场景再处理局部问题。chat（短回复、日常对话、评论）允许口语，但不该端着说话。status（站会更新、进度同步、复盘摘要）保住时间线、动作、结果、风险这四项的结构，不揉进流畅叙述。docs（操作文档、技术说明、接口说明、FAQ、事故复盘）以可检索、可复现、术语稳定优先，不做整篇重写。public-writing（公开帖、对外文章、观点写作）语域一致，不装有洞见。docs、status 和代码注释场景默认不做以语感为目标的第二遍复扫；第二遍会让语气变口语、变广告或影响保真时，停在第一遍。

**通过条件。** 本条与 ALL-G-007 同时生效，各判各的：ALL-G-007 的六档是判据层，决定按哪一档阈值查，配 ALL-G-008 的强度取值与 ALL-PROC-053 的形式线索判定；本条决定输出成什么形态、保不保结构、做不做第二遍。两条给出的方向不一致时按 ALL-PROC-058 分层，两条都在判据层，取更严的一边，判据层不得扩大授权。本条不定改写力度，那一轴由 ALL-PROC-005 按用户措辞定。子场景由文本信号触发，可以落在任一主场景之内，见 ZH-G-003。

**已知会漏掉什么。** 混合文本的主场景要人判，本条只给「只保留一个主语域、其他语域的内容留在必要信息层面」这条处理原则，判不出该保留哪一个。代码注释在四类主场景里没有单列，只在复扫约束那一句里出现。四类是为中文技术写作划的，英文侧不套这张表。

- 正例：一条进度同步按 status 处理，改写后仍然按时间线、动作、结果、风险的顺序分行，只删掉开头的套话，不做第二遍复扫。
- 反例：同一条进度同步被改写成一段流畅的叙述，风险项被并进正文中段。违反点：status 场景要保住的四项结构被揉掉了，读者要读完整段才知道有没有风险。

### ZH-G-003 六个子场景的发布目的

**判据。** 文本命中以下任一子场景的信号时，不依赖用户是否明说，也不受主场景初判限制，都按该子场景处理。README（项目介绍、快速开始、安装方式、功能列表）第一屏说清这是什么、给谁用、解决什么问题。发布说明（版本标题、Added／Changed／Fixed、changelog）列清本版变更、验证和限制，不写发布宣言。论坛帖（社区帖、发帖复盘）保留维护者的真实观察和社区语气，不改成公告。issue 或 PR 回复（bad case、复现、下一版补 benchmark）先确认问题和下一步，不做客服式安抚。接口文档（endpoint、参数字段、类型或默认值、状态码、鉴权）删宣传和元评论，接口合同缺失只标待确认，不替作者补。FAQ 或排障问答尽早给结论或动作。

**通过条件。** 子场景只收束发布目的和语气，不覆盖受保护片段、命中强度和回读规则；有人拿「这是 README 的写法」来绕开保真规则时，按 ALL-PROC-023 的裁决顺序驳回。主场景的语域限制仍然生效，见 ZH-G-002。

**已知会漏掉什么。** 六个之外的发布结构没有条目：公告、白皮书、招聘帖落在主场景里处理。信号词重叠时本条没有优先级：一份 README 里嵌了 FAQ 小节时，两个子场景的要求同时成立，冲突要人判。

- 正例：一段文字里出现了安装命令和功能列表，用户没说这是 README，仍按 README 子场景处理，把第一屏改成一句说清它是什么、给谁用的话。
- 反例：文本里有版本标题和 Added／Changed／Fixed 列表，因为用户没说这是发布说明，就只按主场景 public-writing 改成一段通顺的叙述。违反点：子场景信号已经命中，却以「用户没明说」为由不触发，本版的限制项也随之被叙述吞掉。

### ALL-G-004 不改换带权威含义的发布结构

**判据。** 指出改写稿使用的发布结构，与原文的发布结构不同即命中。两种最常见：采访、对谈或讨论式问答被整理成 FAQ 小节；个人笔记被整理成公告或规范。FAQ 和公告带官方答案的含义，套上去等于给一段个人观点加了背书。

**通过条件。** 用户明确要求转换体裁时按用户的来，并按 ALL-PROC-057 在输出里声明这次做了体裁转换。同一体裁内部该怎么写不归本条，归 ALL-G-002 和 ZH-G-003。

**已知会漏掉什么。** 权威含义的强弱本条不分档：从随笔改成「指南」算不算换结构，边缘情形要人判。署名、出处和发布主体的改动不在本条覆盖范围。

- 正例：一段两人对谈保留原来的问答形态和口语，段落顺序不动，只清掉套话。
- 反例：把同一段对谈整理成「Q：……A：……」的 FAQ 小节。违反点：讨论式问答被换成了带官方含义的发布结构，读者会当成正式答复照着做。

### ZH-G-001 英文排版模式不套用到中文

**判据。** 判定的第一步是看被改写的那个标题或引号属于哪种语言。两处只对英文成立的排版模式不套到中文正文上：标题大小写（Title Case）在中文标题上不适用，不据此改写中文标题的写法；直引号与弯引号的判定对象是中文里夹的英文引文，不是中文引号本身。

**通过条件。** EN-P-012 要求英文标题用句子大小写，本条给它划边界：中文标题不进那条规则的判定范围。EN-P-037 管英文直引号与弯引号跟随原稿，本条同样划出边界：中文引号不按那条判，按 ZH-P-025 的全篇统一口径处理。中英混排文本里的英文片段仍然按 patterns-en.md 判，本条只挡住把英文口径套到中文成分上。

**已知会漏掉什么。** 这里只列了两处排版模式。其他只对英文成立的形态（连字符复合修饰语、缩写的点号、序列逗号）没有逐条划界，遇到时按同一条思路处理：先看这个成分是哪种语言的。

- 正例：遇到中文标题时跳过大小写检查，只判这个标题本身是不是套话。
- 反例：把中文正文里的“……”当成命中弯引号模式，全部替换成英文直引号。违反点：针对英文排版的规则被套到了中文引号上，改完之后中文正文的引号样式反而不统一了。

## 三 语境档位与触发强度

### ALL-G-007 六个语境档位各自的主要风险

**判据。** 判定语境时按六档定位，每一档记的是这个体裁里的主要风险。短社交帖：碎片句和视觉排版本身有用，风险在标签与排版堆砌。通用长文：默认档，所有规则全强度。技术长文：技术术语放行，风险在术语被当成词表命中改掉。商务与投资邮件：受众信任成本高，一切收紧，宣传腔是最大的风险。文档：清晰与可检索优先于声口。随意语域（Slack、内部记录、快速回复）：只处理最严重的一类。档位由 ALL-PROC-053 的形式线索判定，并按那一条把判定结果亮出来。

**通过条件。** 本条只给档位的定位，每一档下各条规则的强度取值在 ALL-G-008。与 ALL-G-002 的分工是：那条给体裁叠加的形态限制，本条给该盯哪一类风险。与 ZH-G-002 的关系见本文件开头和那一条：两张表同时生效，各判各的，冲突时按 ALL-PROC-058 取更严的一边。本条是 ALL-PROC-058 判据层里的语境这一条轴。EN-P-084 的词表例外只在技术长文档位下查。

**已知会漏掉什么。** 六档的名字去掉了平台专名，平台之间的格式差别不在这里，归 ALL-P-003。进度同步在六档里没有对应的档位，中文侧由 ZH-G-002 的 status 承担，英文侧没有。一段文本同时像两档时本条不仲裁，要人定或按 ALL-PROC-003 问。

- 正例：处理一份 README 时定在文档这一档，清晰优先，为长文散文写的节奏规则在这里放宽，术语重复保留。
- 反例：处理一份 README 时按通用长文这一档全强度执行，把重复出现的字段名换成近义词以避免单调。违反点：档位选错，为另一个体裁写的强度被套了上来，改完之后文档搜不到那个字段。

### ALL-G-008 语境档位只调触发门槛，不整组跳过

**判据。** 语境档位对单条 pattern 类规则取三种强度之一。标准：按规则原本的门槛查。放宽：提高触发门槛，只处理明显的。加严：连边缘情形也标，用在受众信任成本高的档位上。没有写进强度表的规则一律按标准强度在所有档位执行。protection 类规则和 ALL-PROC-010 的四组检查不取强度，任何档位下都照常执行。

**通过条件。** 与 ALL-PROC-010 的边界是这样划的：那条管四组检查不得整组跳过，本条管单条 pattern 规则的触发门槛可以按档位调整；本条不设「完全不审」这一档。上游的 skip 取值不采纳，它想要的效果（Slack 消息不必按长文口径查破折号频率）由「放宽」这一档承担。某条规则在某个体裁下确实一次都不该触发时，按 ALL-PROC-025 写进项目自己的 style guide，由用户显式关掉，并按 ALL-PROC-057 在输出里声明。EN-P-056 在长文档位上按本条放宽门槛，它的判据不变。

**已知会漏掉什么。** 本仓库没有逐条规则乘六个档位的强度表，只有三个取值和「未列入即标准强度」这条兜底，具体某条规则在某一档取哪一档强度要执行者按该档的主要风险判断（ALL-G-007）。不设 skip 的代价是随意语域下仍会产生低价值命中，那些命中按 ALL-PROC-056 的执行强度上限处理，不必清零。

- 正例：处理一条 Slack 消息时，破折号频率、加粗数量这类排版规则按放宽档只处理明显的；同一条消息里的事实保护规则照常全查。
- 反例：处理一条 Slack 消息时把破折号频率按长文口径逐处标出，并把整段重写成结构完整的说明。违反点：随意语域这一档该放宽的规则被按标准档执行，而放宽的对象本来只有触发门槛，不包括改动幅度。

## 四 个性按体裁分组

### ALL-G-006 哪些体裁可以有个性

**判据。** 个性的处置按体裁分两组。博客、随笔、观点和个人写作：作者原文已有的观点、犹疑、幽默、跑题一律保留，不因为看起来不齐整就改掉。参考、技术、法律和事实性文本：保持中性，原文没有的第一人称和评价不加。两组都不新增原文没有的个性。

**通过条件。** 第二组里原文已经有的声口按 ALL-PROT-017 保留，但不放大。给本该平实的文字硬注入个性同样算 AI 味，这一点写在 ALL-PROC-018 里，本条给的是「哪些体裁算本该平实」的判据，两条配套使用。

**已知会漏掉什么。** 跨在两组之间的体裁本条没有归档：技术博客、工程复盘、带作者判断的评测，它们既是事实性文本又允许作者出场，落在哪一组要人定。「保留但不放大」里的放大程度也没有可数的口径。

- 正例：一篇个人随笔里作者写了一句自我修正和一处跑题，改写后原样留着，只清掉套话开场。
- 反例：给一份 API 参考文档的改写稿加上「我个人特别喜欢这个接口的设计」。违反点：这是第二组的体裁，本该中性，加进去的第一人称评价原文里也没有。
