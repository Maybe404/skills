# 中英文都适用的模式

这一份收 language 为 both 的写法模式：判据不依赖具体词汇，中文和英文文本上都成立，所以既不放进中文表也不放进英文表。用法是拿一段文字对着每条的「判据」圈出违反的位置，再用「通过条件」排掉不该算的命中。

同一个现象如果中英各有自己的词表或阈值，具体取值不在这里：中文侧在 patterns-zh.md，英文侧在 patterns-en.md，本文件只给不依赖语言的那一层判据。本文件的全部条目都让位于 protection.md，两边同时命中时按 ALL-PROC-023 的裁决顺序先办 protection。

## 一 节奏与结构

### ALL-P-001 句长和段落结构要有变化

**判据。** 句子层按语言分别数。英文分三档：短句 3 到 8 词、中句 12 到 20 词、长句 25 到 40 词，同一段里连续三句以上落在同一档即命中。中文不按词数分档，按字数数：同一段里连续三句以上字数相差在 3 个字以内即命中。段落层看整篇：段落长度整齐划一，或者连续几段用同一种开头句式，也是命中。

**通过条件。** 句长一致本身不是 AI 的证据，按 ALL-M-002 不得单凭这一项下判断，它只是改写时的目标。中文侧按 ZH-M-001 不套英文的词数分档，也不算句长方差，那套指标在中文上没有定义。有意的首语重复在做说服工作时保留；代词连排（He… He… He…）是普通叙述，不算。

**已知会漏掉什么。** 段落收尾形状的雷同这条数不出来，中文侧归 ZH-P-013、英文侧归 EN-P-048，两条与本条合起来才覆盖一篇文字的节奏可预测性。小节和句式骨架层级的重复归 ZH-M-005，判定对象比本条高一层。已知会误伤本来就该整齐的文本：变更日志、状态更新、参数说明里句长一致是格式要求。交付时还要按 ALL-M-026 说得出结构上动了哪一处，清完词表不等于本条过了。

- 正例（中）：「它快了三倍，服务器账单少了一半。用户没抱怨，这是头一回。」
- 反例（中）：「这个方案降低了运营成本。这个改动缩短了交付周期。这个决定改善了用户体验。」违反点：连续三句都是十一二个字，字数差不到三个字，句式骨架也相同。
- 正例（英）："The cache warms on boot. Once warm, a cold request costs about four milliseconds, which is inside the budget we set in March."
- 反例（英）："The cache warms on boot. The index loads next. The workers then start." 违反点：三句都落在 3 到 8 词的短句档，连续三句同档。

### ALL-P-005 对称骨架不为凑气势

**判据。** 三项抽象名词排比、「不仅……而且……更」、三个结构相同的短句连排，都要核一遍这个项数是从内容里数出来的，还是先定了数再往里填。填出来的即命中。原文已经有的对称骨架要重建结构，只把其中几个词换成近义词不算处理过。

**通过条件。** ALL-PROT-009 认定的固定表述和原文引语即使对称也不动。原文确实有三件事时就写三项，不为了避开「三」这个数量删掉一项：ZH-P-012 主张并列项默认取两项或四项，与本条方向相反，取本条，ZH-P-012 记 rejected；EN-S-008 要求三项清单一律压成两项或一项，同样不取。技术写作里的三项清单常常本来就是事实，按体裁权衡，不按出现次数计。

**已知会漏掉什么。** 判不出一份三项清单到底是不是三件事，这一步只能回原文核对。上游给的「形容词、形容词、和形容词这个模式全篇最多一次」是一条可数的上限，本条没有设，全篇累计次数查不出来。

- 正例（中）：「它够快，也够稳。优不优雅我不好说，反正没再半夜被叫起来过。」
- 反例（中）：「它不仅高效，而且稳定，更兼具优雅、简洁与可扩展性。」违反点：「不仅……而且……更」三连对仗，六个形容词没有一条对应具体事实。
- 正例（英）："The event includes talks and panels."
- 反例（英）："The event features innovation, inspiration, and industry insights." 违反点：三个抽象名词凑成排比，项数不是从内容里数出来的。

### ALL-P-006 拆句合句看信息负载，不看长度

**判据。** 拆的依据是信息负载：一句话塞了三个以上信息点就拆。合的依据是可理解性：语义破碎、单独读不成立的短句合回去。长度本身不是判据，不因为一句长就拆，也不因为一句短就合。

**通过条件。** 句子长但读得通，并且这个长度是作者本人的语感时不拆，按 ALL-PROT-017 保留作者的节奏。为强调而有意用的单个碎句是节奏，不合并。

**已知会漏掉什么。** 信息点怎么数没有更细的口径，同一句在不同读者那里可能数出两个也可能数出四个，边缘情形要人来定。跨句累积的信息负载查不出来：三句各带两个信息点、连着读同样吃力的段落，本条不命中。

- 正例（中）：把「他去了。很晚。很累。」合成「他很晚才疲惫地赶到」。
- 反例（中）：「订单少了以后，公司上个月裁了两百人，主要是华东区的销售岗，赔偿按 N+1 算。」保持原样不拆。违反点：一句里压了原因、动作、范围、赔偿口径四个信息点，超过三个的上限。
- 正例（英）：把一句同时交代时间、地点、原因、结果和评价的长句拆成两句。
- 反例（英）：把 "It broke on Friday, of course, right as everyone was leaving." 拆成三个短句。违反点：原句读得通，拆开只是让它变整齐，删掉的是作者的语气。

### ALL-P-008 段落不应可以随意互换

**判据。** 把两个正文段落对调，读者读不出差别，就说明这些段落是并列堆砌而不是展开的论证。处理方式有三种：合并、删除，或者补出段与段之间真实存在的依赖关系。

**通过条件。** 补依赖关系只能用原文已有的材料，原文没有的依赖不得补，这一条由 ALL-PROT-001 兜住。段落确实彼此独立时还有两个出口：把这部分明确写成列表，或者在改动说明里指出这篇缺一个贯穿的论点，交给作者决定，不替作者造一条线索。清单型和参考型文本里段落本来就可以互换，不适用。

**已知会漏掉什么。** 这条要人读一遍才判得了，正则和词表查不出来。它也判不出段落之间的依赖是不是真的：读起来有承接、实际上是新造的因果，本条不命中，那一层归 ALL-P-009 和 ALL-PROT-005。

- 正例（中）：第三段以「这也是上一节把超时定在 30 秒的原因」开头，删掉第二段之后第三段读不通。
- 反例（中）：一篇文章的五段可以任意互换顺序，读者读不出异样。违反点：段与段之间没有依赖，每段都是自足的模块。
- 正例（英）："Remote work's flexibility is the obvious sell. The harder question is what you lose when nobody overhears anything."
- 反例（英）："Remote work improves balance. Many workers prefer it. Studies show productivity rises. Commuting costs drop." 违反点：四句互相独立，打乱顺序不影响理解。

## 二 施事与具体

### ALL-P-004 指名行动者，用主动语态

**判据。** 两类形态命中。一是抽象事物做只有人能做的动作：「市场奖励」「数据告诉我们」「决定浮现出来」。二是隐藏施事者的无主句和被动式：「已完成配置」「变更被做出」「相关行为在上个月发生」。命中之后的动作是把执行者写出来，用主动语态。

**通过条件。** 原文没有写是谁做的时候，本条不要求补出一个施事者：补一个就是新增原文没有的事实，按 ALL-PROT-001 改成问用户，或者改写成不需要施事者的说法。原文已经写明执行者的，按 ALL-PROT-022 不得改成别人。惯例性的拟人（数据显示、系统重建索引）和集体简称（市场、行业）不算命中。参考类语域里丢主语的碎句是正确形式：README 的功能清单、变更日志条目、参数文档、commit 标题不标记。EN-S-007 是无例外的被动语态禁令，本条只禁隐藏施事者的那一类，取本条。

**已知会漏掉什么。** 道德形容词与副词安在不具能动性的名词上（a courageous decision、负责任的算法）本条查不到，那一半归 EN-P-061，两条各管一边。找不到具体的人时改用 you 把读者放进施事位置这个修法不采纳：它会改动原文的指称范围，那一层归 EN-P-034，本仓库记 reference-only，用户点名要求时才用。

- 正例（中）：「运维把配置回滚了，第二天又提了一版新的。」
- 反例（中）：「经过多轮讨论，形成了初步方案，并在会后进行了同步。」违反点：三个分句都没有主语，读不出是谁讨论、谁形成、谁同步。
- 正例（英）："The file watcher clears the cache whenever you edit the config."
- 反例（英）："The cache is invalidated automatically when the config is changed." 违反点：两处被动式都藏起了执行者，句子里指不出是谁让缓存失效的。

### ALL-P-007 具体化只能用原文已有的材料

**判据。** 能给名字、数字、日期、机制、例子的地方用了抽象词即命中。修法是把抽象表述换成原文已经给出或已经暗示的具体内容。验收时反过来问：改写稿里新出现的每一处具体内容，能不能在原文里指出出处。

**通过条件。** 原文里找不到具体内容时不得自己编，标出缺口去问，这条边界由 ALL-PROT-001 管。承载适用条件、目的、风险和限制的抽象句属于信息，不因为读着抽象就删掉。

**已知会漏掉什么。** 用全称词冒充范围（everyone、all teams）是具体化失败的一种固定形式，本条不单独判，归 EN-P-047。给不出具体内容时最省力的替代品是一句人格担保，那一种归 EN-P-052。十个固定短语上的落地修法（点名那个具体的领域、机制、时间跨度）在 EN-P-063。

- 正例（中）：原文别处写了「部署从两小时到九分钟」，把「效率提升明显」换成这个数字。
- 反例（中）：原文只说「效率提升明显」，改写时写成「效率提升了 40%」。违反点：40% 这个数原文没有，是替原文编的，触发 ALL-PROT-001。
- 正例（英）："The integration cut deploy time from 40 minutes to 4."
- 反例（英）："Several services experience timeout issues." 违反点：原文写了是五个服务里的三个、阈值是 30 秒，改写却退回 several 和 timeout issues。

### ALL-P-009 消除外壳造成的假逻辑关系

**判据。** 拆掉连接词之后，原文各分句的主张是不是都还在。都还在，说明这个逻辑关系是措辞外壳造成的，原文并不真的主张它，可以改写掉。「由于……加上……」式的假并列因果是最常见的一种。

**通过条件。** 原文真的主张这个因果时不动。改写之后不得出现原文没有的新因果链，这一点与 ALL-PROT-005（不得把相关性升级成因果）是同一件事的两面。分不清是行文习惯还是作者真这么想时，按 ALL-PROC-003 去问，不自己定。

**已知会漏掉什么。** 判不出跨句、跨段的假因果：连接词在这一句、被它连起来的主张在上一段时，本条不命中。

- 正例（中）：原文写「由于天气原因，加上大家的努力，项目按时完成」，改成「项目按时完成了。期间遇到天气影响，团队也加了班」。
- 反例（中）：同一句改成「天气原因带来了延误风险，大家的努力抵消了这个风险，因此项目按时完成」。违反点：编出了原文没有的因果链条。
- 正例（英）："The migration finished on time. Two engineers worked the weekend, and the weather delayed one shipment."
- 反例（英）："Because of the weather, and given the team's effort, the project landed on time." 违反点：`Because of … and given …` 把两件互不相干的事说成共同构成了这个结果。

### ALL-P-010 简化的对象是表达，不是信息

**判据。** 改短的那句话，少掉的是词还是信息。简化只处理四类表达障碍：黑话术语、过长的句子、抽象名词、纠缠不清的结构。删掉信息来把句子变短不算简化。

**通过条件。** 用户明确要求精简或缩短时按 ALL-PROT-003 的口径执行，那时压缩是被授权的。目的、适用条件、风险和限制即使对象仍然抽象也属于信息：「为了解决这一痛点」可以压成「为了解决这个问题」，不能因为没写清是什么问题就把这个目的整个删掉。

**已知会漏掉什么。** 一个词到底是黑话还是术语，本条不判，中文侧按 ZH-P-030 分流、英文侧按 EN-P-068 分流。这条也查不出信息在改写里被稀释的情况：字数没少，限定条件却被换成了更宽的说法。

- 正例（中）：把一句塞满行话、五行长的句子拆成两句大白话，信息量不变。
- 反例（中）：原文「为了解决这一痛点，团队加了一层缓存」改成「团队加了一层缓存」。违反点：因为「痛点」抽象就把目的删了，读者不再知道这个动作是冲着什么去的。
- 正例（英）：把一句四行长、嵌了两层从句的说明拆成两句，术语换成常用词，条件一条不少。
- 反例（英）：把 "The endpoint returns 429 when a client exceeds 100 requests per minute." 缩成 "The endpoint rate-limits clients."。违反点：状态码和阈值都被删掉了，短下来的是信息。

### ALL-P-011 不把同一个意思绕几遍

**判据。** 用「换句话说」「也就是说」「简单来说」「In other words」「Put simply」引出的后一句，相对前一句新增了什么信息。答不上来即命中，保留最清楚的一版，删掉重复的转述。

**通过条件。** 后一句确实换了抽象层级，或者给出了前一句没有的限定、数字、例子时保留。教学类文本里先给结论再展开一遍是体裁要求，按 ALL-G-002 判。

**已知会漏掉什么。** 跨段的重复转述数不出来：第一段给了结论、第四段换个说法又说一遍，本条不命中。不带这些引出语的重复转述同样查不到。

- 正例（中）：「它把导出报表的时间从十分钟压到了一分钟。」
- 反例（中）：「它能提升效率。换句话说，它让工作更快。也就是说，它节省了时间。」违反点：三句一个意思，后两句没有新增任何信息。
- 正例（英）："The system answers in 40ms at p99."
- 反例（英）："The system is fast. In other words, it performs well. Put simply, speed is one of its strengths." 违反点：同一个判断绕了三遍，后两句都没有落到具体数字上。

## 三 格式与语域

### ALL-P-002 格式服务内容，不做装饰

**判据。** 逐处问这个格式承担了什么信息。五种形态命中：标题里加 emoji；在句子中间随手加粗一两个词；把本可以两三句说清的内容拆成加粗项目符号列表；给只有两句话的小节加标题；在每个标题前加分割线。

**通过条件。** 术语条目和界面标签的加粗保留，它们的加粗有一条说得出来的规则。项目符号留给本身就是清单的内容：功能对照、分步操作、接口参数。

**已知会漏掉什么。** 上游给的「社交帖行尾可以少量用一到两个 emoji」这个例外本条没有采纳，标题里的 emoji 一律标，短社交帖会因此被误伤，按 ALL-G-008 在该档位下放宽触发门槛处理。「一个大节里最多留一处加粗」这条可数上限本条也没有设。按全文词数与结构元素数的比例算的密度那一层归 EN-P-080，本条是逐个小节判该不该加标题、该不该用列表，两条各管一层。列表已经成立之后各项写成了什么形状归 ALL-P-013。

- 正例（中）：「核心优势就一条：冷启动比上一版快了三倍。」
- 反例（中）：「🚀 **核心优势**：我们的**产品**拥有**强大**的**性能**和**卓越**的**体验**！」违反点：emoji 小标题加上五处加粗，没有一处对应具体事实。
- 正例（英）："Remote work has changed how companies operate. Most employees now want flexible arrangements."
- 反例（英）："Remote work has **fundamentally changed** the way companies operate, with **many employees** now preferring **flexible arrangements**." 违反点：三处加粗背后没有一条共同的规则。

### ALL-P-003 输出格式跟随目标渠道

**判据。** 目标渠道不渲染 markdown，输出里却留着 `**`、`##` 这类标记，即命中。邮件正文、短消息、纯文本文档属于不渲染的一类；长文平台才用完整的标题层级。

**通过条件。** 渠道不明时按 ALL-PROC-003 先问一句，不猜。用户明确说了要保留 markdown 源码（例如稿子要提交进仓库）时按用户的来。

**已知会漏掉什么。** 同一类渠道内部的差别本条不分：纯文本邮件和富文本邮件、支持部分 markdown 的短消息平台，都落在同一档里。本条的一个来源是 metadata-only，只贡献了「按平台特性分类处理格式」这个方向，逐平台的渲染能力清单本仓库没有。

- 正例（中）：同一份稿子发到短消息平台时去掉井号和星号，改成纯文字加换行；发到博客时保留标题层级。
- 反例（中）：把带三级标题和加粗的 markdown 原样贴进不解析 markdown 的群聊。违反点：井号和星号会当普通字符显示在正文里。
- 正例（英）：邮件正文用空行分段、用「1.」编号，不出现任何 `**` 或 `##`。
- 反例（英）：邮件正文写 "Please review the **updated policy** before Friday." 违反点：收件人看到的是带星号的原文，这个渠道不渲染 markdown。

### ALL-P-012 全篇语域统一

**判据。** 指出哪两段属于不同语域，并说出各自的标志：术语密度、人称、句长、感叹。说得出来即命中。技术腔、商业腔、自媒体腔之间跳是最常见的三组。

**通过条件。** 原文本身跨了场景时收敛到一个主语域，其他语域的内容只在必要信息层面保留，不要求把信息也删掉。引用原文、访谈引语里的另一种语域不动，那属于受保护片段。

**已知会漏掉什么。** 识别原文里已有的语域断裂、并据此判断这段是拼接的，那一面归 EN-P-040，本条管的是改写方自己不得造成跳跃，两条是同一现象的检测面和产出面。本条查不出单段内部的轻微漂移：整段读下来语域一致、只有一个短语来自另一种腔调时不命中。分段处理长文时这个问题最容易复发，每段各自改得都好，合起来在几种腔调之间跳。

- 正例（中）：全文用一种语域，术语该出现的地方出现，不掺感叹和口号。
- 反例（中）：「这个模块的 P99 稳定在 200ms 以内，真的是天花板级的表现，家人们冲就完了。」违反点：一句里从技术腔跳到自媒体腔，两半的人称和感叹密度完全不同。
- 正例（英）：一篇工程博客通篇用同一层术语密度，不在段落之间切换成营销文案。
- 反例（英）：一段写 "p99 stays under 200ms across the fleet."，下一段写 "And honestly? That's a game changer." 违反点：后一段的人称、句长和感叹与前一段不属于同一种语域。
