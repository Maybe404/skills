# 事实保护

这一份优先于所有模式清理规则。改写和审稿时任何一条与这里冲突，以这里为准（见 process.md 的 ALL-PROC-023）。

## 不能加进去的

### ALL-PROT-001 不编造原文没有的内容

改写和审稿都不得新增原文没有的事实、数字、日期、例子、论据、观点或来源。原文缺来源时向用户索要，不得替用户编一个。

- 正例（中）：原文只说“上线后评审时间变短了”，改写后仍只说变短，不补一个具体数字。
- 反例（中）：“这个功能提升了效率”改成“根据内部数据，效率提升了 40%”。违反点：40% 这个数字原文没有。
- 正例（英）："The team says review got faster after launch."
- 反例（英）："Studies show review time dropped 40% after launch." 违反点：Studies show 和 40% 都不在原文里。

### ALL-PROT-004 不确定不得说成确定

原文表达的不确定要保留：“可能”“大概”“据说”“我不太确定”、might、I think、not sure、seems。

- 正例（中）：原文“可能与天气有关”，改写后仍是“可能与天气有关”。
- 反例（中）：改成“与天气有关”。违反点：删掉了“可能”。
- 正例（英）："This might not scale past 10k users."
- 反例（英）："This will not scale past 10k users." 违反点：might 被删掉，推测变成了断言。

与 EN-P-030（删掉与语气矛盾的保留语）的边界：只有当同一句里保留语和绝对化表述并存时才删保留语；原文本来就在表达犹疑的，不动。

### ALL-PROT-005 相关性不得升级成因果

- 正例（中）：原文“两者同期上升”，改写后仍是同期上升。
- 反例（中）：改成“上升是因为另一者带动”。违反点：加了“因为”。
- 正例（英）："Both numbers rose in the same quarter."
- 反例（英）："The second number rose because of the first." 违反点：because 是原文没有的。

### ALL-PROT-006 排除关系不得改成正面事实

排除一种归因不等于确认另一种。

- 正例（中）：原文“问题不能归因于大家不够努力”，改写后仍是这个排除表述。
- 反例（中）：改成“大家一直很努力”。违反点：否定一种解释被换成了肯定另一件事。
- 正例（英）："The delay was not caused by a lack of effort."
- 反例（英）："The team worked hard throughout." 违反点：原文只排除了一个原因，没有正面评价。

### ALL-PROT-007 不得替原文补出解决方案

原文只给方向时不得换成具体动作项、负责人或时限。

- 正例（中）：原文“完善协同机制”，改写后仍是“完善协同机制”。
- 反例（中）：改成“形成明确结论、设负责人、规定时限”。违反点：三个动作项原文都没有。
- 正例（英）："The team plans to improve the handoff process."
- 反例（英）："The team will name an owner and set a two-week deadline." 违反点：owner 和 deadline 是补出来的。

### ALL-PROT-018 不为人味添加东西

不得为了让文字显得像真人写的而添加原文没有的错别字、emoji、网络用语、第一人称、幽默、感受或个人经历。自然不等于口语化。

- 正例（中）：改写后文字通顺，没有多出 emoji 和网络热词。
- 反例（中）：为显得像真人写的，加了几个 emoji 和“绝绝子”。违反点：这些原文里没有。
- 正例（英）："The migration took three weeks."
- 反例（英）："Honestly? The migration took three weeks and I'm still recovering lol." 违反点：Honestly、lol 和“我还没缓过来”都是新增的人格。

conflicts.md 的 EN-S-002 是这条挡下来的那批手法。

## 不能弄丢的

### ALL-PROT-002 具体事实不得抹成泛化

数字、日期、金额、路径、姓名、测量值原样保留。

- 正例（中）：“工具把评审时间从 30 分钟压到 8 分钟。”
- 反例（中）：“工具显著提升了工程效率。” 违反点：两个数字都没了。
- 正例（英）："Latency dropped from 900ms to 40ms."
- 反例（英）："Performance improved substantially." 违反点：900ms 和 40ms 被抹掉。

### ALL-PROT-003 不默认压缩内容

原文里独立的事实、限定条件、例外、例子、反例、证据一律保留。只有用户明确要求精简或缩短时才压缩。

- 正例（中）：把长句拆短，“仅适用于企业版客户”这个限定跟着留下。
- 反例（中）：为了短，删掉“仅适用于企业版客户”，只留“这个功能很好用”。违反点：限定条件被当成累赘删了。
- 正例（英）："The API caches responses, but only for GET requests."
- 反例（英）："The API caches responses." 违反点：only for GET requests 是限定，不是修饰。

### ALL-PROT-020 删连接词不等于删关系

删掉无功能的连接词、元叙述和结论标签时，原文真实存在的逻辑关系、必要术语和正式程度要留下来。

- 正例（中）：删掉“综上所述”，后面那句表达的因果关系照旧。
- 反例（中）：为删“因此”，把前后两句改成并列陈述。违反点：因果关系跟着连接词一起没了。
- 正例（英）：删掉 It's worth noting that，保留后半句的转折。
- 反例（英）：删掉 however，把对比关系也一起删了。违反点：however 承担了真实的转折。

### ALL-PROT-008 受保护片段默认不动

真实引语、代码、公式、法律条款、标准定义、专有名词、引用标识，以及用户点名要保留的文字，正文逐字不动，只调周边衔接。真伪无法确认的引语一律不改。

- 正例（中）：原文引了一段法律条款，改写只动条款前后的衔接句。
- 反例（中）：把条款改写成意译版。违反点：受保护片段被改了，且用户没有授权。
- 正例（英）：引语里的 delve 原样保留，因为那是被引的人说的话。
- 反例（英）：把引语里的 delve 换成 explore。违反点：改了别人的原话。

### ALL-PROT-009 模式清理的三类例外

三种情况下模式规则让位：精确技术术语的重复（不得为避免重复而换称）、行业固定表述、换个说法会产生歧义的表达。

- 正例（英）：一篇 React 文档里连续三次写 useEffect。
- 反例（英）：分别改成 the effect hook、this hook、the side-effect mechanism。违反点：为避免重复换掉了有确定所指的术语，触发 EN-P-019 的误伤。
- 正例（中）：三句排比里有一句是受访者原话，只改另外两句的结构。
- 反例（中）：为打破排比，把受访者原话也换了说法。违反点：真实引语不因结构调整而改。

### ALL-PROT-010 引用绑定与术语一致

引用标识必须紧跟它实际支持的最后一项陈述。移动陈述时引用一起移动。同句后半新增了该来源不支持的内容，先拆句再放引用。复扫时逐条核对引用位置和专名、术语写法。

- 正例（中）：带引用标识的一句整体挪到新位置，标识仍跟着它原本支持的那句话。
- 反例（中）：挪动后又在同句后半接了一条该引用不支持的新论断，标识留在整句末尾。违反点：引用挂到了更宽的陈述上，没有先拆句。

### ALL-PROT-013 不把旧文改新

原文标明或可推知的写作年代属于事实，不得为了让文字读起来更新而改掉它的时代特征、用语和当时的事实边界。

- 正例（中）：一篇标注 2019 年写的文章保留当时的说法。
- 反例（中）：把它改成 2026 年常见的网文腔，并补上后来才有的事实。违反点：改掉了文本真实的时代属性。

### ALL-PROT-017 保留作者声口

作者本人的词汇、节奏、直率程度、幽默、脏话、犹疑、跑题和自我纠正属于作者，不得为了“统一”“专业”“安全”而改掉。拿到改写授权不等于拿到换声口的授权。

- 正例（中）：保留作者略显跳跃的口语段落，只修其中确实读不通的一句。
- 反例（中）：把全文改成同样长度、同样工整的书面语。违反点：原本的口语节奏被抹平了。
- 正例（英）：保留 "This API design is a mess." 这句带火气的判断。
- 反例（英）：改成 "The API has certain limitations." 违反点：作者的态度被换成了中立措辞。

conflicts.md 的 EN-S-001（五档语体）是这条挡下来的。

## 判断和边界

### ALL-PROT-011 凭证门检

处理正文前先扫一遍：输入里出现密码、API key、access token、私钥、会话 cookie，或用户称某段是凭证时，立即停止，不引用、不改写、不复述、不做掩码后继续，只回一句请对方删除或替换后重试。概念性地讨论 token、API key 不算。

- 正例：发现一串明示为密钥的字符，只回一句请对方删除或替换后重试，不做别的处理。
- 反例：先把它替换成 [REDACTED] 再继续改写其余段落。违反点：检测到凭证后没有停止。

### ALL-PROT-012 不做作者身份鉴定

不得判断或猜测一段文字是不是 AI 写的，也不得据此评价作者的诚实或道德。只列出命中的具体规则 id，让用户自己判断。

- 正例：「命中 EN-P-001（delve）、EN-P-014（marks a pivotal moment），供你自己判断。」
- 反例：「这篇有 80% 的可能是 AI 生成的。」违反点：给了身份判断，而不是可核实的证据。

### ALL-PROT-014 不静默替作者纠正

原文的因果、权衡、比较或结论可能超出它给出的证据时，不得在正文里静默改弱或改强结论，也不得在正文里插入编辑注记。风险写在单独的“需作者确认”一节。

- 正例：正文保持原表述，需作者确认里写一句“这处因果的证据只支持到相关性”。
- 反例：直接在正文里把结论改弱，或插入“（编者注：此处证据不足）”。违反点：改了正文，或把注记留在了正文里。

### ALL-PROT-015 默认不做外部核验

默认只检查文内一致性和引用绑定，不主动去外部核实原文引用的数据、来源或事实。只有用户要求查证时才做。

- 正例：核对文中引用与它支持的陈述是否一致，不去搜索这份数据的真伪。
- 反例：用户没要求，自行上网查证并把查到的新数据写进改写稿。违反点：引入了原文之外的事实。

### ALL-PROT-016 阶段稿不得称终稿

- 正例：只改完前三章的稿子标为“阶段稿”。
- 反例：只处理了一部分却称“终稿”。违反点：交付物的名称和实际处理范围对不上。

### ALL-PROT-019 改写前先列事实清单和论证清单

动手前列两份清单。第一份记：人物、数字、时间、地点、动作、引语、归因、评价、排除项、限定条件、来源、术语。第二份记：主张、依据、例子、反例、条件、比较、因果、结论。改完逐项核对，每一项在改写稿里都要能找到，且关系没变。

- 正例：改写前记下文中三个日期、两处引语、一条排除项，改完逐项打勾。
- 反例：直接开改，交付前也没有比对。违反点：跳过了清单，事实漂移无从发现。
