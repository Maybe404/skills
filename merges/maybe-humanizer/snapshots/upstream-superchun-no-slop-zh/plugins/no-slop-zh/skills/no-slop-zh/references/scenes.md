# 场景 pack 与难判边界

主场景和默认力度以 `SKILL.md` 为准。pack 是根据用户输入和文稿自动选择的内部规则，不要求用户提供 pack 名。

## 选择规则

按以下顺序匹配：

1. 用户明确说明的发布位置或目标文稿类型
2. 文件名、扩展名和现有文稿结构
3. 主要读者和写作目的

明确匹配时必须加载对应 pack。无法可靠判断时不用 pack，退回大场景默认值；不要为了套结构猜类型。

- 「发到论坛」「论坛主帖」「发帖」→ `forum`
- 「博客」「公众号文章」「专栏文章」→ `blog`
- 「官网介绍」「产品介绍」「公开介绍」→ `public-intro`
- `README`、项目首页 → `readme`
- release note、版本说明、更新日志、changelog → `release-note`
- 状态同步、进展汇报、周报、站会更新 → `status-update`
- 操作手册、接口说明、安装步骤、技术 FAQ → `tech-guide`
- issue/PR 回复、代码评审回复 → `issue-pr`

「落地文档」「定稿」「写入文件」只确定需要最终化，不足以选择 pack。若现有类型与用户指定的目标交付物冲突，以目标交付物为准。

## Packs

pack 的默认结构只用于组织原文已有信息。原文缺少某项时不编造内容，也不为凑结构增加空标题。

README 和公开介绍的首屏不用宣传口号。读者不熟悉的分类词应改成具体问题，例如把「模型腔」「表演腔」「空洞拔高」写成「套话」「重复」「句子不顺」「没有实际内容」。精确产品名和必要术语不受此限制。

### `forum`

- 大场景：`public-writing`
- 默认 voice：`conversational`
- 默认结构：先说问题、判断或请求，再给必要背景和依据，最后落到具体讨论点
- 限制：保留观察与取舍；不改成公司公告、客服安抚或个人表演

### `blog`

- 大场景：`public-writing`
- 默认 voice：`plain`
- 默认结构：主题与判断 → 事实或推理 → 结论；原文已有叙事线时保留
- 限制：不虚构经历、情绪、案例或作者人格

### `public-intro`

- 大场景：`public-writing`
- 默认 voice：`plain`
- 默认结构：是什么 → 给谁用 → 解决什么 → 必要限制
- 限制：删宏大开场和宣传拔高；不补产品能力或效果

### `readme`

- 大场景：`docs-public`
- 默认 voice：`plain`
- 默认结构：第一屏说明是什么、给谁用、解决什么；随后保留原有安装、使用和限制
- 限制：代码、命令、链接和配置不改；不把技术说明改成营销文；首屏直接说明用途，不写宣传口号
- 更新说明只写读者能直接使用的变化；不解释版本为何尚未发布，也不展示内部选择过程、回归数量或测试状态。面向贡献者的 README 或用户明确要求时除外

### `release-note`

- 大场景：`docs-public`
- 默认 voice：`plain`
- 默认结构：改动 → 验证 → 限制或未做项
- 限制：操作步骤和机器状态只做最小编辑；不把未验证写成已完成

### `status-update`

- 大场景：`status`
- 默认 voice：`plain`
- 默认结构：结果或当前状态 → 阻塞 → 下一步
- 限制：动作和需要对方决定的事项放前面；不写自我表扬或过程表演

### `tech-guide`

- 大场景：`docs-tech`
- 默认 voice：`plain`
- 默认结构：目的和前提 → 操作步骤 → 预期结果 → 原文已有的异常处理
- 限制：不改命令、API、状态、条件和执行顺序；不补不存在的排错步骤

### `issue-pr`

- 大场景：`status`
- 默认 voice：`plain`
- 默认结构：结论或确认事项 → 依据 → 下一步
- 限制：保留文件、行号、命令和报错原文；删颁奖、尽职汇报和过度承诺

## 混合文档

只选一个主场景，局部允许降级，不允许升级：

- README / 技术博客中的代码、命令、配置、表格和实现说明：`minimal` 或只保护。
- release note 中的验证步骤、错误原文和未做项：`minimal`，保留限定与状态词。
- postmortem 中的对外摘要：全文仍按 `docs-tech`；不要因摘要可公开而升到 `standard`。
- 论坛帖中的引用、数据和技术片段：按保护项处理，周围观点仍按 `public-writing`。

局部降级只改变编辑力度，不改变全文的 mode 和 scope。

## 难判信号

- 同时出现「要发」与大量操作步骤：按主要读者判断；面向用户选 `docs-public`，面向执行者选 `docs-tech`。
- 同时包含观点和状态同步：若目的在推动协作，选 `status`；若目的在公开论证，选 `public-writing`。
- 用户要求“保留原结构”但未要求保句数：保留标题和段落顺序，scope 仍可为 `structural`。
- 用户要求“不要删任何句子 / 保句数”：使用 `in-place`。
- 文本过长，无法一次完整回读和保真：先分段处理，不截断、不概括未处理部分。

不确定时采用更低力度，并在有实质取舍时用一行改动说明。
