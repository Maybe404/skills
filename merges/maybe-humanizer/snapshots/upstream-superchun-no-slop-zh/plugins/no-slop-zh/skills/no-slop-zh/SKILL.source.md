# no-slop-zh

把套话多、句子绕、意思空的文字改得冷静、清楚、简洁。

所有 Edit 先做基础清理。`voice` 只调整表达方式，不改变事实、结构要求或人格材料。

## When not to use

- 逐字翻译、仿品牌 voice、仿官方通稿腔
- 新增人格、幽默、经历、情绪或故事
- 整篇英文润色（只有限处理中英混写中的常见英文模板语）
- 主体是代码、日志、命令、配置、接口名、报错（可局部清旁白，不动技术片段）
- 事实校对、补研究、写新内容（本 skill 只改表达，不扩写论据）

## Core stance

1. **先保信息，再谈风格。** 不新增事实、数字、功能、来源、时间、因果；不删核心事实；不改责任主体。
2. **最小有效编辑。** 强句、已清楚的逻辑链不动；不为「更整齐」整段重写。
3. **冷静客观。** 删掉没有实际内容的夸奖、宣传、总结和装深刻；保留判断时要有依据或标明是观点。
4. **用词简洁清晰。** 短句优先；一词能说清不用三词；专有名词稳定，不轮换同义词装文采。
5. **逻辑优先于修辞。** 读者应能顺着「前提 → 推断 → 结论 / 下一步」读完；删掉打断这条链的空承接。
6. **缺信息就露缺口。** 无源权威只有在原文已有独立证据时才删铺垫；否则标明来源缺口。**禁止**补虚构机构/数据/年份。
7. **不擅自增加个人语气。** 原文没有的「我」「老实说」「令人不安」等不要加。
8. **协作场景从轻。** status/docs 默认轻改、术语保守；对外与长文才允许更大结构清理。

## Output modes

### Edit（默认）

输出：

1. 改后全文（单一推荐版）
2. 仅当改动涉及多段、结构或保真取舍时，附极短 **改动说明**（1–5 条，只写实质变化）
3. `bounded` 中若有整句空话未擅自删除：把正文标为 **待确认稿**，并附 **建议删除（待确认）** 清单

短文本只有局部降调时，只输出改后全文，不强制附编辑说明。

提交前用同目录 `eval.md` 自检；任一项 fail 先修再交。

### Detect / annotation

用户说「先标问题」「哪里像 AI」「只审不改」时启用。

- 只输出最重要的 **1–5** 个问题点
- 每点固定四字段：`问题族` | `触发点（引文）` | `建议动作` | `是否建议改写`
- **不要**附完整重写稿
- 标完可一句询问是否进入 Edit

## 基础清理与 voice

基础清理是所有 Edit 的必经步骤，不是可选风格：删除套话、重复内容和无实际作用的引导或总结，修正生硬语序，保留事实、术语和责任主体。

`voice` 只有三种：

- **plain（默认）**：直接、自然、克制；使用常见词和正常中文语序。
- **conversational**：在 plain 之上放松句式和节奏，适合论坛、评论和叙述性长文；不增加人格表演。
- **formal**：使用完整、稳定的书面语，适合正式对外文本；不增加官话、宣传腔或确定程度。

兼容旧说法：

- `clean` / `default` → 基础清理 + `voice=plain`
- `natural` /「自然一点」/「说人话」/「口语化」/「拟人化」→ `voice=conversational`
- 「正式一点」/「正式文风」→ `voice=formal`

用户明确指定的 voice 优先于 pack 默认值。若 voice 与技术结构冲突，保留结构、术语、命令和状态，只在允许范围内调整语序与措辞；不报错中断，也不静默改写成另一种任务。

`conversational` 和 `formal` 都必须遵守：

- 只使用原文已有的人称、情绪和个人判断
- 不新增感慨、幽默、经历、故事、套近乎或品牌 voice
- 不改变事实、论据、确定程度、责任主体和 scope
- `docs-tech`、`status`、release note 和操作步骤只做表层语序与措辞调整，不改变固定结构

## Execution

先完成共同准备：

1. **判模式**：默认 Edit；用户要求先标问题、不改写时选 Detect
2. **判大场景**：从五个场景中选一个；按主要读者和目的判断
3. **判 pack**：用户明确发布位置或文稿类型时优先；其次看文件名、内容、主要读者和目的。类型明确时必须读取 `references/scenes.md` 并加载对应 pack；无法可靠判断时不用 pack，不猜
4. **解析 voice**：用户明确指定 > pack 默认值 > `plain`
5. **划保护项**：逐字锁定值与标记；语义锁定主体、归因、因果、限制与不确定性
6. **判操作歧义**：含糊动作若可能改变系统、数据、时间或责任，且上下文未说明是查看、演练还是执行，先只问一个澄清问题；得到答案后再 Edit

### Edit branch

1. **定力度和 scope**：由大场景、pack、用户约束和文本长度决定；混合文档的局部只可降级，不能升级
2. **做基础清理**：按问题族清理，词表只兜底（`references/patterns-zh.md`）
3. **做 voice 调整**：只在大场景和 pack 允许的范围内调整节奏、句式和常用表达
4. **保真回读**；仍有残味再做只许轻量修的 Residual Audit
5. 对照 `eval.md` 的共同项、voice 项及对应 pack 项；所有硬门通过后输出

### Detect branch

1. 按问题族选最重要的 1–5 个问题，并逐字引用触发点
2. 结合保护项判断是否建议改写；不输出完整重写稿
3. 只跑 `eval.md` 的 Detect 专用项；全部通过后输出

保护项的精确边界见 `references/protected.md`。README、release note、论坛帖、博客、公开介绍、状态同步、技术操作文档或 issue/PR 等类型明确时，必须读 `references/scenes.md`；混合或难判场景也读该文件。处理具体口癖时读 `references/patterns-zh.md`。只有 `SKILL.md` 时也必须能完成无 pack 的基础改写。

### 文件输入与写回

用户给出文件路径时，使用宿主提供的文件或文档工具读取，不要求用户重新粘贴全文。

- `.md` / `.txt` 等纯文本：按原编码与结构处理；Markdown 保护项仍适用
- Word、PDF 等复合格式：只有宿主能可靠保留版式时才写回；否则输出改后文本并说明未覆盖原文件
- 用户只说「检查」「先标问题」时不写文件
- 用户说「处理」「润色」但未要求覆盖时，默认生成同目录 `<原名>.cleaned.<扩展名>`；若文件已存在，不静默覆盖
- 用户明确说「修改 / 覆盖 / 原地编辑 <路径>」时才写回该文件
- 写回前完成保真检查；不得把代码块、表格、front matter、链接目标或复合文档版式静默降级成纯文本

## Scenes（默认力度）

| 场景 | 信号 | 默认力度 | 默认 scope |
|------|------|----------|------------|
| `public-writing` | 博客、长文、公开介绍、论坛主帖、对外观点 | `standard`，套话和空话集中时可 `aggressive` | 长文（≳1000 字）→ `bounded`；短文 → `structural` |
| `docs-public` | README、release note、changelog、安装说明 | `standard` | `structural`（列表结构可保留） |
| `status` | 进度同步、站会、协作更新 | `minimal` | `structural` 但少并句 |
| `docs-tech` | 接口/操作文档、复盘、FAQ | `minimal` | `structural`；**禁止**升 `aggressive` |
| `chat` | 短回复、评论 | `minimal` | `structural` |

混合文本只选一个主场景。代码块、表格、front matter、技术说明等局部可降到 `minimal` 或只保护；局部不得高于主场景力度。对外与自读优先按 `public-writing` / `docs-public` 处理。

### Pack 路由

pack 是内部派生规则，不要求用户填写名称。选择顺序：

1. 用户明确说明的发布位置或文稿类型
2. 目标文件名和已有文稿类型
3. 主要读者和写作目的
4. 仍不明确时不用 pack，只用大场景默认值

用户说「发到论坛」可直接选论坛 pack；「落地文档」「定稿」「写入文件」只表示需要最终化，不能单独确定 pack。用户要求把现有文稿改成另一种交付物时，以目标交付物为准。

pack 只组织原文已有信息，不补写缺失事实。匹配条件、默认 voice、默认结构和专属检查见 `references/scenes.md`。

## Editing controls

### 力度

- **minimal**：只改局部套话和空收尾
- **standard**：统一语域、删除套话和空话，必要时并句/换主语
- **aggressive**：仅高影响问题族密集或结构全盘模板时；`docs-tech` 不用

### Scope

| scope | 行为 | 何时 |
|-------|------|------|
| `structural` | 可删空句、轻量并句/调序 | 短文、明确要求重写 |
| `bounded` | 句内必洗；**整句空话进待确认清单**，不擅自删 | `public-writing` 长文默认 |
| `in-place` | 不删整句、不并句、不重排；只句内降调 | 用户要求保句数/完全原样 |

`aggressive + in-place` 若用户坚持可用，但须先满足保真；优先建议 `standard + bounded`。

## 无源引用（三选一）

| 模式 | 行为 | 默认场景 |
|------|------|----------|
| `rewrite-safe` | 原文已有独立证据时，删权威铺垫并保留原有确定程度 | `public-writing`、`chat` |
| `audit-only` | 点明缺来源；不改成「已证实」口吻 | `docs-tech`、`status` |
| `rewrite-with-placeholder` | 保留论证位置并写明「此处待补来源」 | 仅用户明确要求保留结构时 |

如果判断唯一的支撑就是「研究表明 / 数据显示」等权威铺垫，不得删掉铺垫后留下更强的裸断言；改用 `audit-only` / placeholder，或在 scope 允许时删除整条无支撑判断。**禁止**补具体机构、论文名、数据、年份。

## 必砍 / 必留（单文件兜底）

### 必砍或改写

- 开场：值得注意的是、让我来、你说得很对、一针见血、Great question
- 收尾：综上所述、归根结底、本质上、希望这对你有帮助、激动人心的时代
- 骨架：不是 X 而是 Y → 多数直接说 Y；不仅仅…更是… 的拔高
- 黑话：能无损改成具体对象、动作或状态时就改；只有替换确实会改变技术含义时才保留原词。行业简称、内部说法和截短词不自动算必要术语。赋能、抓手、兜住、能力矩阵、全新跃迁是代表，不是完整名单；幂等、回滚、控制闭环等标准技术术语保留
- 行业简称与截短词：面向该领域专业读者且属于固定术语时可以保留；其他情况按语境使用能指明实际对象、动作或状态的最短常见说法。例如把「现网」写成「线上」或「生产环境」，把「待拍」写成「尚未决定」，把「拍下一组」写成「先决定哪一组」。短说法有歧义时，只补充区分含义所需的信息
- 含糊或截短动作：看动作实际作用于什么，不因前面的「回滚」「部署」等修饰词判断。方案、文案、步骤、清单等内容，包括回滚步骤，可改为查看、检查或核对。若不同理解会决定只是查看、演练还是真正执行，并会改变系统、数据、时间或责任，则上下文明确后才改；流程名称本身不表示要执行。原文未明确实际动作时，按上面的操作歧义步骤先询问
- 无源：研究表明、数据显示、专家认为、studies show（按上表三模式）
- 旁白：这说明了什么、真正理解了用户、方向是对的（无论据时）
- 推销：要不要我顺便…你一句话的事

### 必留（除非用户明确要求改且不损信息）

- 逐字保护项与语义不变量（见 `references/protected.md`）
- 系统/组件作主语的技术事实；可改病句，不改行为、条件与责任主体
- 承载关键事实的抽象句（可降调，不删信息）
- 原文已有的限定与不确定性（可能、尚未验证）——冷静文风需要诚实边界

### 默认文风校准

改完应接近：

- 冷静、客观，少情绪词
- 逻辑链清楚：先结论或先事实均可，但前后要接得上
- 用词短、准；能砍的修饰就砍
- 允许保留必要专业术语与轻微不对称句长
- **不要**：段子感、鸡汤、假共情、整齐排比装气势、每句同等抛光

## Residual Audit（第二遍，可选）

仅当保真已通过、仍有轻模板感时做；只允许：

- 删一个残留开场/收尾
- 拆一处过满句或合并两句过匀空壳
- 把一句旁白压回直接判断

禁止：全文重写、补事实、改术语与责任。

`docs-tech` / `status` 默认更常停在第一遍。

## Output contract

**Edit**

```text
<front matter>                ← 原文有则逐字保留
【待确认稿】                   ← 仅 bounded 且有未删整句时；放在 front matter 后的正文首行
<改后全文>

### 改动说明                  ← 仅多段、结构变化或有保真取舍时
- …

### 建议删除（待确认）        ← 仅 bounded 且有未删整句时
- 「原文…」— 删了不丢信息，因为…
```

待确认清单中的原句必须仍逐字存在于正文；已经改写或删除的句子不得列入清单。

**Detect**

```text
1. 问题族：…
   触发点：「…」
   建议动作：…
   是否建议改写：是/否
```

高风险误杀时最多多一行：`保留了系统主语/术语，避免失真。`
